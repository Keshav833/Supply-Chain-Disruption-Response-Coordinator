"A supplier is late. Who decides what happens next?"
Welcome. Today I'm presenting a multi-agent system that answers a simple but critical question: when a supply chain disruption happens, who should decide the response? Our system delegates that decision to a network of specialized agents that collaborate on a shared blackboard, ensuring every decision is backed by evidence and validated independently. Let me walk you through how it works, what makes it resilient, and what we learned building it.

The Problem: Manual Supply Chain Response

❌ Manual Process

  • Humans check email and sheets
  • Call suppliers, routes separately
  • Decisions based on incomplete info
  • Slow and error-prone

⚠️ Plain LLM Issues

  • Hallucinates supplier capacity
  • No auditability of reasoning
  • Can't be corrected post-decision
  • No safety guardrails

✓ Our Objective

Automated, deterministic, auditable decisions using specialized agents on a shared blackboard with zero LLM hallucination and complete decision traceability.

The challenge is that manual decision-making is slow and inconsistent, while unconstrained LLMs can't be trusted with critical supply chain decisions—they hallucinate data, provide no audit trail, and can't be corrected if they make a mistake. Our solution combines the structure of a blackboard architecture with deterministic tools and an independent validation gate, so every decision is evidence-backed and verifiable. All five agents run concurrently, publish their findings to the shared blackboard, and the Coordinator makes the final call using only the evidence on the board, never touching raw data directly.

The Five Agents

Monitor

Validates report & identifies affected sites

Tools: validate_disruption, identify_affected_sites

Writes: incident_assessment

Inventory

Checks warehouse stock & replenishment need

Tools: get_inventory, calculate_stock_shortage

Writes: inventory_findings

Supplier

Finds alternatives & validates capacity/lead time

Tools: find_alternative_suppliers, check_supplier_capacity

Writes: supplier_findings

Route

Locates alternative routes & checks viability

Tools: get_available_routes, calculate_route_delay

Writes: route_findings

Coordinator

Decides from Blackboard evidence only. Zero access to raw data.

Tools: read_blackboard_evidence, validate_mitigation_decision

Writes: mitigation_decision + notifications

Each agent has exactly two tools—deterministic Python functions that query our in-memory datasets. All agents are specialized: the first four gather evidence in parallel, and the Coordinator runs only after all evidence is collected. The key insight is that the Coordinator never accesses the raw datasets directly. It only reads the published evidence on the shared blackboard. This enforces a clean separation: computation is distributed, but decisions are centralized and auditable.

Blackboard Architecture

Key Design Principles

  • Agents never talk directly. All collaboration via Blackboard.
  • Write-once, owner-only. Each agent owns one section. Lock enforced.
  • Evidence status tracking. AVAILABLE, UNKNOWN, or FAILED.
  • Coordinator is blind. No raw data access; reads snapshot only.
  • Independent validation gate. Every decision re-checked deterministically.
  • Append-only audit log. Every run, every tool call, complete trace.
The blackboard is a classic pattern for multi-agent systems. Here's how ours works: First, the incident comes in. The Monitor validates it and publishes an assessment. If valid, Inventory, Supplier, and Route agents run concurrently using asyncio.gather—each with its own timeout. Each agent publishes exactly one section to the blackboard and can't modify it again. The Coordinator then reads a snapshot of all published evidence—not the original datasets—and makes a decision. That decision goes through an independent validation gate. Finally, the entire trace is appended to a JSONL log. If any agent times out or fails, its section stays empty and the Coordinator sees that as FAILED evidence, not as a gap to guess about.

Let me walk you through one real execution. We ran INC-1001: a supplier delay affecting LAPTOP-001 at Pune warehouse. 100 units needed in 7 days, but the primary supplier is 12 days late. The Monitor confirmed it's high severity. Inventory checked Pune's local stock: only 25 units, with 40 reserved as safety buffer. So 115 units need to come from elsewhere. Supplier agent checked alternatives: SUP-02 can deliver 150 units in 3 days, well within the deadline. Route agent looked for indirect paths—WH-MUM-02 has 90 usable units, but we need 100, so that route is not viable. The Coordinator had one choice: REORDER from SUP-02. That decision passed the final validation, and the run was logged with a unique ID and complete trace. The whole thing took 20 milliseconds.

Design Strengths: Why This Matters

🔒 Typed Pydantic Board

Every blackboard section and log entry is strictly typed. Schema violations are caught immediately.

✍️ Write-Once, Ownership Enforced

Each agent owns one section. Writes are protected by asyncio.Lock. No overwrites or conflicts.

📊 Evidence Status Tracking

AVAILABLE, UNKNOWN, or FAILED. Coordinator knows exactly which evidence is trustworthy.

🛡️ Zero LLM Hallucination Risk

All tools are deterministic Python functions over in-memory data. No hallucination possible.

⏱️ Automatic Retries & Timeouts

Transient failures retry with backoff. Each agent has a 60-second timeout. Bounded, predictable.

📜 Append-Only Audit Log

Every run, every tool call, every decision logged to JSONL. Never rewritten or deleted.

🚫 Coordinator Blind to Raw Data

Test-proven: Coordinator cannot access inventory.json, suppliers.json, routes.json. Only reads Blackboard.

✅ Independent Validation Gate

Every decision is re-validated deterministically before persisting. Invalid decisions are rejected.

Let me highlight the core strengths of this design. First, everything is typed with Pydantic, so schema errors are impossible. Second, we enforce write-once semantics with asyncio.Lock, so there's no race condition where two agents accidentally overwrite the same section. Third, we track whether each piece of evidence is AVAILABLE, UNKNOWN, or FAILED—the Coordinator never guesses; if evidence is missing, it stays missing. Fourth, all tools are deterministic Python functions, not LLM calls, so hallucination is impossible by construction. Fifth, we have automatic retries and timeouts for resilience. Sixth, the entire audit trail is appended to a JSONL file—useful for compliance and debugging. Seventh, and most critically, the Coordinator has zero access to the raw datasets. It can only read the evidence the other agents published on the blackboard. This is enforced at the type-level: the Coordinator's input contains only a snapshot of the blackboard, not the datasets. And eighth, every decision goes through an independent validation gate—deterministic re-checking against the evidence.

Questions?
So to summarize: we built a system that automates mitigation decisions for supply chain disruptions. It outputs one of four decisions—REORDER, REROUTE, HOLD, or UNKNOWN—with full justification and a list of parties to notify. Every decision is logged with complete traceability. We achieved 100% accuracy on our evaluation set. The honest limitations: we're working with simulated data, decisions are advisory only and require human sign-off, the live LLM feature needs internet connectivity, and our evaluation was on five carefully chosen scenarios, not millions of real incidents. In the future, we'd integrate real data sources, add a human authorization workflow, track deliveries in real time, potentially have the LLM negotiate with suppliers in multiple rounds, and add a cost optimization agent. This was a learning exercise in distributed decision-making and supply chain automation, and I think we've shown that a blackboard architecture with deterministic tools and independent validation is a solid foundation for critical systems.

E. Likely Viva Questions & Answers

Q: Why a blackboard and not direct agent communication?

Blackboards decouple agents. If agents communicated directly, one failure could cascade. With a blackboard, evidence is published independently, and the Coordinator reads a snapshot only. Failure of one agent doesn't corrupt the evidence of others.

Q: How does the Coordinator avoid hallucinating decisions?

The Coordinator has zero access to raw datasets. It reads only Blackboard evidence. All tools are deterministic Python functions. The decision logic is a typed rule engine over published evidence, not an LLM. If evidence is missing or failed, the decision is UNKNOWN—never guessed.

Q: What if an agent times out or fails?

Each agent has a 60-second timeout. If it exceeds that, asyncio.wait_for cancels it and the agent is marked FAILED. The Coordinator sees that agent's section as FAILED evidence, not UNKNOWN. The decision still proceeds using available evidence from other agents.

Q: How is auditability ensured?

Every run, every tool call, every Blackboard write, the final decision, and the validation result are logged to an append-only JSONL file. Each run has a unique ID. The log is never truncated or rewritten. It's machine-readable for compliance and debugging.

Q: Why not use a plain LLM for all decisions?

LLMs hallucinate. For supply chain decisions, hallucinating supplier capacity or delivery times is catastrophic. Our deterministic tools query actual data. We only use LLM for prose interpretation, never for factual claims. The decision logic is deterministic rules.

Q: What is ExecutionMode and why does it matter?

Every run is labelled deterministic_fallback or semantic_kernel_llm. We never label fallback output as LLM. Deterministic fallback means all tools ran without live LLM calls. This label is essential for understanding decision trust and reproducibility.

Q: How do you prevent race conditions on the Blackboard?

Each Blackboard section is owned by one agent. Writes are protected by asyncio.Lock. Only the owner can write, and only once. The lock ensures atomicity. Post-publication, other agents can read but not write.

Q: What is the difference between HOLD and UNKNOWN?

HOLD is a valid decision: "no feasible mitigation exists; hold and escalate." It's used when all options are exhausted but evidence is complete. UNKNOWN is used when evidence itself is missing or failed—we can't decide at all. UNKNOWN triggers data-owner escalation.

These are the questions you'll likely face in a viva. The key themes: separation of concerns via the blackboard, elimination of hallucination via deterministic tools, auditability via append-only logs, failure resilience via timeouts and fallback logic, and clear execution-mode labelling so you always know if a decision is deterministic or LLM-influenced.
